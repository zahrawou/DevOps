## **<u>The answers:</u>**

To untrack it you need `git rm --cached .env` , but the old commits still contain it. If it held a real secret, you must also rotate it.

## **Exercise 2.** 

(a) Why Git cannot merge these two changes automatically? 

(b) How is that different from merging two changes to two _different_ challenges in the same file? (c) A check for conflict markers can run automatically, so that nobody needs to remember the grep. Where can this check run? 

## **<u>The answers:</u>** 

**(a)** Both branches changed the _same line_ in the same file, each starting from the same original value (500). Git can see two different new values, but it has no way to know which one is correct. That is a decision about meaning, not text, so Git stops and asks a human. 

**(b)** If the two branches had changed _different_ challenges (different lines, not touching each other), Git would merge both changes automatically with no conflict, even though they are in the same file. Git works line by line (in “hunks”), not file by file. 

**(c)** The check can run in a **Git hook** , for example a local `pre-commit` hook that refuses a commit if the file contains `<<<<<<<` . Better still, it can run on the server side as a **CI job** (for example GitHub Actions on every push or pull request), because a local hook can be skipped with `--no-verify` .

## **<u>The answers:</u>**

Commit `5ea852d` (“read the key from the environment”) did not delete anything. It only added a new snapshot on top of `3d6fb4b` , where the key still exists. Gitleaks points exactly there: `Commit: 3d6fb4b` , `Line: 119` . To really remove the key you would have to rewrite `3d6fb4b` itself. That would change its hash, and every later commit’s hash too. 

**(d)** If someone pushed a _real_ key, the first two steps are: 

1. **Revoke (rotate) the key** at the provider right away, so the old one stops working. 

2. **Check the provider’s logs** for any use of the key since it was pushed, to see if it was already abused.

## **Exercise 5.** 

- (a) People often see branch protection as a quality measure. Explain in three or four lines why it is also a _security_ control. 

- (b) Name the attack that it makes harder. 

- (c) On a free GitHub account, the repository must be public for this part. Why? 

## **<u>The answers:</u>** 

**(a)** Branch protection means nobody can change `main` alone. Every change must go through a pull request, and a second person has to read and approve it first. If one developer’s account or laptop is compromised, the attacker cannot push malicious code straight into the main branch, because the change would still need a reviewer’s approval. Blocking force pushes and deletions also stops anyone from rewriting or erasing the history, so the record of who changed what stays trustworthy. So the rule protects the code that everyone trusts and deploys, not only its quality. 

**(b)** A **supply-chain attack through code injection** : an attacker who has stolen a maintainer’s credentials silently inserts a backdoor or malicious code into the project. The same rule also limits insider threats, where one person tries to push harmful code without anyone noticing. 

**(c)** On a free GitHub account, branch protection rules are available only for **public** repositories. Private repositories need a paid plan (Pro, Team or Enterprise) to use them. That is why the lab asks for a public repo.
